PART 1

The mental model, and the two sides

NAC3 is a contract between a web UI and the agents that drive it: voice runners, LLM intermediaries, RPA bots, accessibility tools and end-to-end test suites. It does not replace ARIA or React: it sits on top of whatever you already render with.

The four things the contract specifies

PieceWhat it solvesWhat it looks like
NamesSo an agent can ask "click save" and have it resolve to exactly one DOM node.data-nac-id="invoice.save" — a dotted path, unique within the plugin, stable across re-renders and across redesigns.
VerbsSo the agent calls NAC.click(id) with no per-app glue.data-nac-action="save" plus the runtime's imperative verbs.
The ackSo the agent knows when the side effect finished, not when the click started.nac:action:succeeded and its deterministic family per role.
ProvenanceSo a downstream system can tell a human click from a synthesised one.is_trusted in the event detail, and an HMAC over the manifest.

The two sides, and why this manual always separates them

Every NAC3 feature is used from one of two places, and confusing them is the most expensive mistake you can make reading the specification.

Side A — the adopter · React, Angular, PHP, whatever

This side declares: it paints the five attributes in its own DOM, registers a manifest, and emits the ack event when its side effect has finished.

If the adopter does not emit the ack, the agent eats the timeout and the action is reported as a failure. It is beginner mistake number one.

In this manual, the examples for this side are in React.

Side B — the agent · Python, Node, a model, a bot

This side consumes: it reads the published catalogue (NAC.describe() from inside the page, or api/latest/contract.json from outside), decides, and dispatches one structured action.

It never invents an identifier. If the name it wants is not in the tree it was given, it asks instead of guessing.

In this manual, the examples for this side are in Python.

The Python scaffold every example uses

The runtime is browser JavaScript. A Python agent drives it from outside through one of two doors, and both appear throughout the manual:

  • Door 1 — inside the page, with Playwright for Python: page.evaluate() runs window.NAC.* in the page context and returns the result. This is the door tests and bots use.
  • Door 2 — no browser: the contract catalogue is published as data at api/latest/contract.json and api/latest.json. An agent that only needs to know what exists and how it is named does not need to open a browser.

Setup on the Python side: pip install playwright && playwright install chromium. This repository does not declare it as a dependency: there is no Python here.

The scaffold, once. Every Python example in part 3 assumes this class is imported:

#!/usr/bin/env python3
# nac_agent.py -- agent-side scaffold. It does NOT live in the repository:
# it is the code this manual proposes for consuming the contract from Python.
import json, urllib.request
from playwright.sync_api import sync_playwright

class NacPage:
    """An agent driving a NAC3 page from Python."""

    def __init__(self, page):
        self.page = page
        self.page.wait_for_function("() => window.NAC && window.NAC.describe")

    # --- reading ------------------------------------------------------
    def version(self):
        return self.page.evaluate("() => [NAC.version, NAC.spec_version]")

    def describe(self):
        """The tree: the only thing the agent knows about the screen."""
        return self.page.evaluate("() => NAC.describe()")

    def manifest(self, slug):
        return self.page.evaluate("s => NAC.manifest(s)", slug)

    # --- writing ------------------------------------------------------
    def call(self, verb, *args):
        """Dispatch a runtime verb and return {ok} or {error, code}.
           Every contract failure arrives as a NacError; we turn it into
           data so the code survives -- the code is the actionable part."""
        return self.page.evaluate(
            """async ([v, a]) => {
                 try { return { ok: true, value: await window.NAC[v](...a) }; }
                 catch (e) { return { ok: false, code: e.code || null,
                                      message: String(e && e.message),
                                      candidates: e.candidates || null }; }
               }""",
            [verb, list(args)])

    # --- acks ---------------------------------------------------------
    def listen(self, *event_names):
        """Set up a mailbox in the page BEFORE acting. The ack is an
           event: if you start listening after dispatching, you lost it."""
        self.page.evaluate(
            """names => {
                 window.__bus = window.__bus || [];
                 for (const n of names)
                   document.addEventListener(n, e =>
                     window.__bus.push({ type: n, detail: e.detail }));
               }""",
            list(event_names))

    def inbox(self):
        return self.page.evaluate("() => window.__bus || []")

Installing on the adopter's side

By package: npm install @nac3/runtime. Two imports, in this order: import '@nac3/runtime' and then import '@nac3/runtime/extensions'. The order is not decorative — the extensions module refuses to install and logs an error if the core was not loaded first.

By script tag: <script src="https://yujin.app/nac-spec/js/nac.js"> and then nac-v2-extensions.js.

What each one brings. The core brings everything imperative, the introspection, the capabilities, the authority, the snapshot versioning, the plugin extension contract and the v2.5 blocks. The extensions bring the brownfield primitives, the HMAC, the runtime's own i18n catalogue and the entire data-table family (dt_*). Calling dt_add_row without the extensions loaded does not fail with a contract error: it is undefined.

The trap of section 6.3

The DOM click event fires before the handler runs. The contract needs to know when the side effect finished, not when the click started. Hence a separate family. If your handler is asynchronous, the ack is emitted after it resolves, not before.

The ten locales, and the only one that governs

Every label_i18n must cover all ten: es en pt fr ja zh hi ar de it. During a brownfield migration, i18n_strict: 'permissive' on NAC.autoRegister.watch() accepts partial coverage; production ships all ten.

Two different things that always get confused

The ten locales of the manifest are a requirement on the adopter: they are the labels an agent reads to name an element in the user's language.

The ten locales of the normative document are something else: English is normative, the nine translations are machine-made, partial and non-normative, each declares in a banner which English revision it covers, and where they disagree English governs. A translation behind the English never blocks the English from publishing.

The features, one by one

Thirty-four cards. Each one carries: what it does, the signature, a React example on the adopter's side, a Python example on the agent's side, the exact command that proves it, and a coverage tag. The tags mean this, and it is worth checking them before trusting anything:

in the battery  the test runs with cd runtime && npm test or with npm run check:release.
outside the battery  the test exists and passes, but nobody runs it automatically: it is an orphan suite, or it needs a browser.
no test of its own  no test in this tree exercises it directly.

The first thing to know about coverage

The publication chain never runs the runtime battery. Verified 2026-11-14 by reading .github/workflows/deploy.yml: its 24 steps run locks for integrity, version, published contract, translations, stylesheets and mount path — and none of them executes cd runtime && npm test. The 15 suites and their 453 assertions run only in prepublishOnly, that is, at the moment of publishing to npm by hand, and when someone runs them.

Practical consequence: "the chain is green" does not mean "the runtime's behaviour was tested on this push". The runtime battery is run by hand, and that is why it is the first command of part 4.

A · Declaring: the manifest and its locks

Nothing works before this. The manifest is the source of truth the agent reads.

F01

register · unregister · manifest · syncPlugin · list_registered_plugins

in the battery

Registers a plugin's catalogue. register appends if the slug already exists; syncPlugin replaces. That difference is the whole card: in a single-page host, where a component may remount, calling register twice accumulates duplicate entries and syncPlugin does not.

NAC.register(manifest) → void (throws under strict validation) NAC.syncPlugin(manifest) → void /* idempotent: replaces */ NAC.unregister(plugin_slug) → void NAC.manifest(plugin_slug) → Manifest | null NAC.list_registered_plugins() → string[]

Required fields: plugin_slug (must match the data-nac-plugin of the host element) and nac_version (the runtime rejects a manifest claiming a version higher than its own). Optional: elements[], tabs[], fields[], actions[], kpis[], data_tables[]. Each elements[] entry needs id and role.

F02

STRICT_VALIDATION — register throws instead of warning

in the battery

With true (the default since 2.3) NAC.register() throws an Error with code='strict_validation' and a findings array on any of these three:

  • manifest_role_unknown — the entry's role is outside the 20 canonical ones.
  • tab_id_manifest_role_drift — the id starts with tab. and the role is not tab.
  • manifest_dom_role_mismatch — the mounted element's data-nac-role differs from the role the manifest declares.
NAC.STRICT_VALIDATION = true /* 2.2: false (warn only) · 2.3+: true (throws) · 3.0: the flag is removed */

To opt out during a migration it must be set to false before the first register() call. Afterwards it has no effect.

React — the migration window, and how to close it

HARD_DEDUP — one slug, one plugin

in the battery

With true (the default) register throws on the first slug-uniqueness violation, and a boot-time pass paints a red banner on the page and dispatches nac:fatal. The flag is removed in 2.6: enforcement becomes unconditional.

B · Acting: the imperative verbs

The eight verbs that write. All return a promise, all reject with NacError, and all emit provenance even when they fail.

F04

click — fire an action and wait for its ack

in the battery dedicated suite is orphaned

Resolves the (plugin, nac_id) pair against the registry and the DOM, checks the capability gate and the snapshot gate, dispatches the click, waits for the contract event and only then resolves the promise. The default timeout is config.default_timeout_ms, which is 5000.

NAC.click(nac_id, opts?) → Promise<{ok:true}> opts: { plugin?, expected_plugin_version?, expected_tree_version?, expected_element_state_hash? } rejects: not_found · invalid · disabled · hidden · capability_required · timeout · snapshot_stale · version_required
Failure number one of every adoption

If the adopter's handler does not emit nac:action:succeeded, the agent waits five seconds and gets timeout. And the action happened. The specification requires treating a timeout as a real failure, so the agent reports a failure for something that worked. The fix is NAC.bindAction (F11), not a longer timeout.

React — the ack emitted by hand, and the exact moment

async function onSave() {
  await api.saveInvoice(draft);     // the REAL side effect
  // Only now. Before this, the ack is a lie.
  document.dispatchEvent(
    new CustomEvent('nac:action:succeeded', {
      bubbles: true, composed: true,
      detail: { plugin: 'invoice',
                action_id: 'invoice.save' }
    }));
}

function onSaveFailed(err) {
  document.dispatchEvent(
    new CustomEvent('nac:action:failed', {

F10

invoke · utter — actions that carry data

in the battery

Up to 2.2 every action was click-and-go: the agent fires, the host does whatever it does. That works for save or cancel and collapses when the action needs data from the agent: search(query), upload(file), schedule(date), utter(text). A synthetic click has no way to carry a payload.

NAC.invoke(action_id, payload, opts?) → Promise<{ok, request_id, ack}> NAC.utter(action_id, {text, lang?, voice?, metadata?}) → Promise<...> /* utter ≡ invoke(id, {verb:'utter', text, lang}) */ default timeout: 30,000 ms (against 5,000 for click)

The runtime dispatches nac:action:requested on the host element, with {action_id, verb, payload, plugin, request_id, ts}. The host processes it and emits nac:action:succeeded — or :failed — with the same request_id. The runtime correlates by that id and resolves the agent's promise.

Four obligations on the host, and one prohibition
  1. Declare actions[].payload_schema in the manifest entry.
  2. Listen for nac:action:requested.
  3. Emit :succeeded with the request_id echoed back, or :failed with its error.
  4. Never emit a :succeeded with a request_id it did not receive. That is what prevents cross-talk between concurrent invocations.
And what to know before trusting the schema

payload_schema is informational. The reference runtime does not read it at all: it accepts it in a manifest, carries it in NAC.manifest() and never validates against it. STRICT_VALIDATION covers manifest/DOM role findings; it has never covered payloads. An agent must not assume its payload was validated because a schema was declared: today the only validation that happens is the one the agent does before sending. It stays an open, undated question in section 13 of the normative text.

Second trap: invoke does not reject when the element has disabled or aria-disabled. The disabled attribute is a click guard, and invoke is a logical request, not a synthetic click. A host that needs to refuse based on UI state must do it in its nac:action:requested listener. click, by contrast, still rejects.

Three different gates, routinely confused with one another. None of the three is a permission system.

F16

Capabilities — fast rejection before dispatch

in the battery

The manifest declares which capability an action requires, and the runtime checks it before dispatching. The agent gets capability_required immediately, instead of a full round trip that fails server-side with a 403 several seconds later.

NAC.setCapabilities(caps: string|string[]|null) /* replaces the whole set; null clears it */ NAC.grantCapability(cap) · NAC.revokeCapability(cap) /* incremental */ NAC.userCapabilities() → string[] /* snapshot */ /* in the manifest: */ requires_capability: 'finance.delete_invoice' /* element level */ requires_capability: ['finance.approve','finance.admin'] /* array = OR */

Verb level wins over element level if both are present. For AND semantics you declare separate gated actions or compose it at the host level. On click the gate runs after not_found, disabled and hidden, so the most specific failure surfaces; on invoke it runs before the request event fires, so the host never sees an unauthorised attempt.

What this is NOT, said by the landing itself

The capability gate is a usability optimisation and an intent-level signal: it is not a security boundary. The adopter's server must still authorise every call. A malicious agent running with the user's access can do anything the user can, and NAC3 does not protect against that. It is written on the landing, in the "what it does not cover" section, and in the specification.

Shadow DOM: open roots automatically, closed roots by invitation

in the battery

Open roots: the runtime resolves through them recursively and automatically. No manifest hint and no opt-in required.

/* algorithm, for a selector S against a root R */ 1. R.querySelector(S) → if non-null, return immediately 2. for every descendant el of R: if el.shadowRoot is non-null → recurse with R := el.shadowRoot, depth +1 else if el.nac3 is an object with query() → delegate (closed root) 3. depth cap: 10 levels. Deeper than that → not_found 4. walk is DOM order: siblings before nested shadows. First match wins /* reference internals */ _deepQuery(selector, root) · _deepQueryAll(selector, root)

Closed roots: a browser boundary, not a NAC3 decision. The runtime cannot reach inside unless the component author voluntarily exposes a surface.

interface NAC3HostInterface { query(selector): Element | null; /* MANDATORY */ queryAll(selector): Element[]; /* recommended */ describe?(): Array<{id, role, action?, label?}>; /* optional */ } /* diagnostic events, deduped per host with a WeakSet, ONCE per page load */ nac:shadow_blocked { host, reason: 'exposure_threw'|'not_exposed', ts } nac:shadow_protocol_violation { host, message, value_snapshot, ts }
Three obligations on the component author
  1. Put data-nac-id, data-nac-role and data-nac-action on the operable elements inside the shadow.
  2. Set composed: true on every nac:* event it emits manually. Without it the event stops at the boundary and the runtime's correlation machinery never sees it. The runtime's own events already carry composed:true.
  3. Avoid <slot> for anything that must stay isolated: slotted nodes live in the light DOM and are resolved there.

The benefit of voluntary exposure: a conformant agent works against design systems with closed-shadow components — Salesforce Lightning, some GitHub Primer components, security-sensitive widgets — with no per-component adapter. The cost is opting in, component by component.

The plugin extension contract — canvas, iframes and own APIs

in the battery

The largest card in the manual, and the one that solves what NAC.click cannot: send a Send_UNO_Command postMessage to a Collabora iframe, call figma.currentPage.selection = [...], invoke excalidrawAPI.setElements(...) on a React ref, or read whether Bold is active on the current selection — which the toolbar reflects and the canvas hides.

The fix was not to extend NAC.click with backend-detection heuristics. It was to add an explicit, agnostic verb that takes a plugin slug and a verb path, and lets the plugin's manifest declare how it is routed. The runtime knows nothing about any specific app: it learns how to talk to one by reading the manifest.

NAC.registerPlugin(slug, manifest) → void /* pure JSON manifest, no callbacks */ NAC.call(plugin, verb_path, args?) → Promise<any> NAC.read(plugin, state_path) → Promise<any> NAC.subscribe(plugin, event_path, cb) → SubscriptionHandle NAC.unsubscribe(handle) → void /* synchronous and idempotent */

Verbs and events have exactly one binding. State has an ordered array. read walks the array in order and returns the first source that resolved; if every one fails, it rejects with state_unreadable and err.attempts carries one entry per attempted backend with {backend, reason}. The chain encodes the author's preference: the fastest, cheapest, freshest source is declared first.

They say the protocol could not get there, never why the application said no. A plugin that needs a code of its own — a row that is not materialised, a locked document, an export still rendering — raises it under the reserved prefix plugin.:

The 2.6 fail-closed rule, and the defect that produced it

synthetic-mutation resolves every observed state path to the element its primary dom-mirror binding selects. When a selector matches nothing, subscribe must reject with backend_target_missing, naming the paths and selectors that did not resolve, and must not return a handle.

Why: a subscription that observes nothing resolves successfully and then never fires — which is precisely the silent damage this protocol exists to remove. And until 2.5.2 that is what the reference runtime did.

A manifest whose observed node legitimately comes and goes — the row of a virtualised grid, which exists only while scrolled into view — declares root: a container that outlives the node. The runtime then observes the container with subtree: true and re-resolves the selectors on every mutation, so a subscription taken while the node was absent fires when the node mounts. The move from unknown to known is the change the caller is waiting for, so that transition is itself an emit.

The six 2.6 hooks: discovery and self-description

in the battery

Until 2.5.2 the extension registry was readable by exactly three functions (call, read, subscribe), so an agent that did not register the plugin itself could not learn it exists. It read the DOM manifest, found the chrome, and the canvas surface was invisible. For a surface that declares no DOM at all — a voice-only plugin — there was nothing to find whatsoever.

/* discovery */ NAC.plugins() → PluginDescriptor[] /* ordered by slug */ NAC.describePlugin(slug) → PluginDescriptor /* API handles, for objects that never land on window */ NAC.registerApiHandle(name, obj) · NAC.unregisterApiHandle(name) → boolean NAC.apiHandles() → string[] /* self-description, all optional */ verb: label · hint · params[] params: {name, type, required?, unit?, min?, max?, enum?, label?, hint?} state: label · hint · unit event: label · hint
The five rules of discovery, and why each one
  1. Both are SYNCHRONOUS. They read a local object; nothing is dispatched to any surface, so there is no reason for an agent to await a round trip just to find out what is there.
  2. The descriptor is a COPY. A caller must not be able to reach the live registry through it and rewrite another plugin's routing.
  3. It comes back sorted by path, so two reads of the same registry are byte-comparable.
  4. An undeclared label, hint or params reads as null, never as a missing key: a reader does not have to tell "absent" from "not declared".
  5. describePlugin on an unregistered slug rejects with plugin_not_registered.

Discovery is deliberately a read of what the manifest declares, not a probe of the surface. It tells an agent what exists and how to name it; whether the surface answers today is what call and read are for.

And what self-description closes: on a continuous surface the actionable thing is the argument — a coordinate and a zoom, an instant on a timeline, a page and a form field, a pose in three dimensions — and until 2.5 nothing declared its shape, its unit or its range. A voice runner could not even name the verb out loud.

And an explicit limit

params declares the shape of the args object NAC.call receives. The runtime does NOT validate args against it. The declaration exists so an agent can compose a call and a voice runner can speak it; a surface that needs its arguments enforced enforces them where they land.

And none of it is translated by the runtime: a label is authored in the app's language, and a host that speaks another one localises at its own layer.

A single function for screen readers, text-to-speech, voice flows, audit logs and mobile assistive surfaces. It returns null if the plugin or the id cannot be found.

Closes the silent-damage gap: the agent confirms the effect of an action, not that the command went out. Both compose with NAC.read(), so they work against any of the nine backends of F26.

NAC.expect(plugin, statePath, value, opts?) → Promise<value> opts: { timeout_ms = 5000, poll_ms = 100, comparator = (current, expected) => current === expected } /* a read that fails during polling is RETRIED until the deadline: it is treated as "not yet observable", not as a hard error */ rejects: NacError('timeout') NAC.diff(plugin, statePath, actionFn) → Promise<{before, after, changed}> /* reads, awaits actionFn(), reads again. changed is computed with a JSON.stringify compare, so undefined-vs-value also flags as changed. Boot, deferred replay and the test harness

the boot, in the battery the harness, no test

When the module installs it does five things, in this order, and they are worth knowing because they explain almost every boot problem:

  1. Installs global.NAC with its exported keys.
  2. Guards against a double install with the __nac_v1_installed flag.
  3. Dispatches nac:installed carrying { version, spec }.
  4. Mounts the ARIA bridge, so data-nac-a11y-hint actually reaches a screen reader. It runs after install, and appends to existing aria-describedby values rather than overwriting them.
  5. Replays window.__NAC_PENDING__, the buffer the host staged before the runtime existed, then clears it so a hot reload does not double-replay.
/* the boot buffer: the host stages {event, detail} BEFORE the runtime loads */ window.__NAC_PENDING__ = [{ event: 'nac:action:succeeded', detail: {...} }, ...]; NAC.replay_pending(buffer) /* replay by hand, if the automatic pass is not enough */ /* harness: the runtime can test itself */ NAC.assert_event_fired(type, opts?) · NAC.assert_event_count(type, n) NAC.perf_probe(...) · NAC.set_perf_tolerance(...)

Browser-only init is guarded: the module is importable in Node, in SSR and in the test suite without crashing. That is precisely what lets the 15 suites run in Node with no browser.

The three conformance levels

its lock needs a browser, outside CI

A level is written NAC3 Conformance Level 1, 2 or 3. A conformance claim must cite the identifier published in api/latest/levels.json — nac3-conformance-level-<1|2|3> — never a display name.

Why they were renamed in 2.5

They used to be written NAC-1, NAC-2 and NAC-3. That is one dash away from the protocol name: "this page is NAC-3 conformant" could not be told apart from "this page implements NAC3", and an agent asked to report a level had no unambiguous string to report. The old names stay readable as historical aliases (legacy_display_name beside the level they belonged to) but are not normative.

LevelWhat it requires, on top of everything the previous one requires
1Every clickable widget an agent should be able to operate carries data-nac-id and data-nac-role · every action fires nac:action:succeeded after its side effect · the page registers at least one manifest · NAC.click(id) works for every advertised id.
2Declares explicit tabs[], fields[] and actions[] in the manifest, not inferred from the DOM · label_i18n covering all ten locales for every user-facing label · implements the v2.0 brownfield primitives · passes validate_global({probe:false}) with zero error-severity findings.
3HMAC-signed manifests · distinguishes isTrusted for sensitive verbs · passes validate_global({probe:true}) with zero findings, of any severity.

5.3 · The six declared blind spots

What this manual cannot see from where it looks
  1. The runtime's resolution internals. js/nac.js is 8,740 lines. What was read is the public export, the install block, the version constant and the header.
