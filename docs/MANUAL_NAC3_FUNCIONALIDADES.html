PARTE 1

El modelo mental y los dos lados

NAC3 es un contrato entre una interfaz web y los agentes que la manejan: corredores de voz, intermediarios con modelo de lenguaje, robots de automatización, herramientas de accesibilidad y suites de pruebas de punta a punta. No reemplaza a ARIA ni a React: se apoya encima de lo que ya renderizás.

Las cuatro cosas que el contrato especifica

PiezaQué resuelveCómo se ve
NombresQue un agente pueda pedir «hacé clic en guardar» y eso resuelva a un solo nodo del DOM.data-nac-id="invoice.save" — ruta con puntos, única dentro del plugin, estable entre renders y entre rediseños.
VerbosQue el agente llame NAC.click(id) sin pegamento por aplicación.data-nac-action="save" + los verbos imperativos del runtime.
AcuseQue el agente sepa cuándo terminó el efecto, no cuándo empezó el clic.nac:action:succeeded y su familia determinista por rol.
ProcedenciaQue un sistema aguas abajo distinga un clic humano de uno sintetizado.is_trusted en el detalle del evento, y HMAC sobre el manifiesto.

Los dos lados, y por qué este manual los separa siempre

Toda funcionalidad de NAC3 se usa desde uno de dos lugares, y confundirlos es el error más caro que se puede cometer leyendo la especificación.

Lado A — el adoptante · React, Angular, PHP, lo que sea

Es quien declara: pinta los cinco atributos en su propio DOM, registra un manifiesto, y emite el evento de acuse cuando su efecto terminó.

Si el adoptante no emite el acuse, el agente se come el tiempo de espera y la acción queda reportada como falla. Es el error de principiante número uno.

En este manual, los ejemplos de este lado van en React.

Lado B — el agente · Python, Node, un modelo, un robot

Es quien consume: lee el catálogo publicado (NAC.describe() dentro de la página, o api/latest/contract.json desde afuera), decide, y despacha una acción estructurada.

Nunca inventa un identificador. Si no encuentra el nombre en el árbol que le dieron, pregunta en vez de adivinar.

En este manual, los ejemplos de este lado van en Python.

El andamio de Python que usan todos los ejemplos

El runtime es JavaScript de navegador. Un agente de Python lo maneja desde afuera por una de dos puertas, y las dos aparecen a lo largo del manual:

  • Puerta 1 — adentro de la página, con Playwright para Python: page.evaluate() corre window.NAC.* en el contexto de la página y devuelve el resultado. Es la puerta que usan las pruebas y los robots.
  • Puerta 2 — sin navegador: el catálogo del contrato se publica como datos en api/latest/contract.json y api/latest.json. Un agente que sólo necesita saber qué existe y cómo se llama no necesita abrir un navegador.

Instalación del lado de Python: pip install playwright && playwright install chromium. Este repositorio no la declara como dependencia: no hay Python acá.

El andamio, una sola vez. Todos los ejemplos de Python de la parte 3 asumen que esta clase está importada:

#!/usr/bin/env python3
# nac_agent.py -- andamio del lado agente. NO vive en el repositorio:
# es el codigo que este manual propone para consumir el contrato desde Python.
import json, urllib.request
from playwright.sync_api import sync_playwright

class NacPage:
    """Un agente que maneja una pagina NAC3 desde Python."""

    def __init__(self, page):
        self.page = page
        self.page.wait_for_function("() => window.NAC && window.NAC.describe")

    # --- lectura -------------------------------------------------------
    def version(self):
        return self.page.evaluate("() => [NAC.version, NAC.spec_version]")

    def describe(self):
        """El arbol: lo unico que el agente sabe de la pantalla."""
        return self.page.evaluate("() => NAC.describe()")

    def manifest(self, slug):
        return self.page.evaluate("s => NAC.manifest(s)", slug)

    # --- escritura -----------------------------------------------------
    def call(self, verb, *args):
        """Despacha un verbo del runtime y devuelve {ok} o {error, code}.
           Toda falla del contrato llega como NacError; la convertimos en
           datos para no perder el codigo, que es lo accionable."""
        return self.page.evaluate(
            """async ([v, a]) => {
                 try { return { ok: true, value: await window.NAC[v](...a) }; }
                 catch (e) { return { ok: false, code: e.code || null,
                                      message: String(e && e.message),
                                      candidates: e.candidates || null }; }
               }""",
            [verb, list(args)])

    # --- acuses --------------------------------------------------------
    def listen(self, *event_names):
        """Arma un buzon en la pagina ANTES de actuar. El acuse es un
           evento: si lo escuchas despues de disparar, lo perdiste."""
        self.page.evaluate(
            """names => {
                 window.__bus = window.__bus || [];
                 for (const n of names)
                   document.addEventListener(n, e =>
                     window.__bus.push({ type: n, detail: e.detail }));
               }""",
            list(event_names))

    def inbox(self):
        return self.page.evaluate("() => window.__bus || []")

Instalación del lado del adoptante

Por paquete: npm install @nac3/runtime. Dos importaciones, en este orden: import '@nac3/runtime' y después import '@nac3/runtime/extensions'. El orden no es decorativo — el módulo de extensiones se niega a instalarse y escribe un error si el núcleo no se cargó primero.

Por etiqueta: <script src="https://yujin.app/nac-spec/js/nac.js"> y después nac-v2-extensions.js.

Qué trae cada uno. El núcleo trae todo lo imperativo, la introspección, las capacidades, la autoridad, el versionado de instantánea, el contrato de extensión de plugin y los bloques 2.5. Las extensiones traen los primitivos de migración progresiva, el HMAC, el catálogo de idiomas del runtime y toda la familia de tablas de datos (dt_*). Llamar a dt_add_row sin las extensiones cargadas no falla con un error del contrato: es undefined.

La trampa de la sección 6.3

El evento click del DOM dispara antes de que corra el manejador. El contrato necesita saber cuándo terminó el efecto, no cuándo empezó el clic. De ahí que exista una familia aparte. Si tu manejador es asíncrono, el acuse se emite después de resolver, no antes.

Los diez idiomas y el único que manda

Todo label_i18n debe cubrir los diez: es en pt fr ja zh hi ar de it. Durante una migración progresiva, i18n_strict: 'permissive' en NAC.autoRegister.watch() acepta cobertura parcial; en producción van los diez.

Dos cosas distintas que se confunden siempre

Los diez idiomas del manifiesto son un requisito sobre el adoptante: son las etiquetas con las que un agente nombra un elemento en el idioma del usuario.

Los diez idiomas del documento normativo son otra cosa: el inglés es el normativo, las nueve traducciones son automáticas, parciales y no normativas, cada una declara en un cartel qué revisión del inglés cubre, y donde difieran gana el inglés. F01

register · unregister · manifest · syncPlugin · list_registered_plugins

en la batería

Registra el catálogo de un plugin. register agrega si el slug ya existe; syncPlugin reemplaza. Esa diferencia es toda la ficha: en un anfitrión de página única, donde un componente se vuelve a montar, register dos veces acumula entradas duplicadas y syncPlugin no.

NAC.register(manifest) → void (lanza bajo validación estricta) NAC.syncPlugin(manifest) → void /* idempotente: reemplaza */ NAC.unregister(plugin_slug) → void NAC.manifest(plugin_slug) → Manifest | null NAC.list_registered_plugins() → string[]

Campos obligatorios: plugin_slug (tiene que coincidir con el data-nac-plugin del elemento anfitrión) y nac_version (el runtime rechaza un manifiesto que declare una versión mayor que la suya). Opcionales: elements[], tabs[], fields[], actions[], kpis[], data_tables[]. Cada entrada de elements[] necesita id y role.

invoke · utter — acciones que llevan datos

en la batería

Hasta la 2.2 toda acción era clic y listo: el agente dispara, el anfitrión hace lo que hace. Eso funciona para save o cancel y se derrumba cuando la acción necesita datos del agente: search(query), upload(file), schedule(date), utter(text). Un clic sintético no tiene por dónde llevar una carga útil.

NAC.invoke(action_id, payload, opts?) → Promise<{ok, request_id, ack}> NAC.utter(action_id, {text, lang?, voice?, metadata?}) → Promise<...> /* utter ≡ invoke(id, {verb:'utter', text, lang}) */ tiempo de espera por omisión: 30 000 ms (contra 5 000 de click)

El runtime despacha nac:action:requested sobre el elemento anfitrión, con {action_id, verb, payload, plugin, request_id, ts}. El anfitrión procesa y emite nac:action:succeeded —o :failed— con el mismo request_id. El runtime correlaciona por ese identificador y resuelve la promesa del agente.

Cuatro obligaciones del anfitrión, y una prohibición
  1. Declarar actions[].payload_schema en la entrada del manifiesto.
  2. Escuchar nac:action:requested.
  3. Emitir :succeeded con el request_id devuelto, o :failed con su error.
  4. Nunca emitir un :succeeded con un request_id que no recibió. Eso es lo que evita el cruce entre invocaciones concurrentes.
Y lo que hay que saber antes de confiar en el esquema

payload_schema es informativo. El runtime de referencia no lo lee en absoluto: lo acepta en el manifiesto, lo acarrea en NAC.manifest() y nunca valida contra él. STRICT_VALIDATION cubre hallazgos de rol entre manifiesto y DOM; nunca cubrió cargas útiles. Un agente no debe suponer que su carga fue validada porque había un esquema declarado: hoy la única validación que ocurre es la que el agente hace antes de mandar. Queda como pregunta abierta y sin fecha en la sección 13 del texto normativo.

Segunda trampa: invoke no rechaza cuando el elemento tiene disabled o aria-disabled. El atributo deshabilitado es una guarda de clic, e invoke es un pedido lógico, no un clic sintético. Un anfitrión que necesite negarse por estado de interfaz tiene que hacerlo en su escucha de nac:action:requested. click, en cambio, sí sigue rechazando.

Capacidades — rechazo rápido antes de despachar

en la batería

El manifiesto declara qué capacidad exige una acción, y el runtime la chequea antes de despachar. El agente recibe capability_required en el acto, en vez de una vuelta completa que falla con un 403 varios segundos después.

NAC.setCapabilities(caps: string|string[]|null) /* reemplaza todo el conjunto; null lo limpia */ NAC.grantCapability(cap) · NAC.revokeCapability(cap) /* incrementales */ NAC.userCapabilities() → string[] /* instantánea */ /* en el manifiesto: */ requires_capability: 'finance.delete_invoice' /* a nivel de elemento */ requires_capability: ['finance.approve','finance.admin'] /* arreglo = O lógico */

El nivel de verbo gana sobre el nivel de elemento si están los dos. Para «Y lógico» hay que declarar acciones separadas o componerlo en el anfitrión. En click la compuerta corre después de not_found, disabled y hidden, para que aflore la falla más específica; en invoke corre antes de que se dispare el evento de pedido, así que el anfitrión nunca ve un intento no autorizado.

Lo que esto NO es, dicho por la propia portada

La compuerta de capacidad es una optimización de experiencia de uso y una señal de intención: no es un límite de seguridad. El servidor del adoptante tiene que seguir autorizando cada llamada. Un agente malicioso que corre con el acceso del usuario puede hacer todo lo que el usuario puede hacer, y NAC3 no protege contra eso. Está escrito en la portada, en la sección «lo que no cubre», y en la especificación.

Shadow DOM: raíces abiertas automáticas, cerradas por invitación

en la batería

Raíces abiertas: el runtime resuelve a través de ellas de forma recursiva y automática. No hace falta ni una pista en el manifiesto ni una opción.

/* algoritmo, para un selector S contra una raíz R */ 1. R.querySelector(S) → si no es null, devolver ya 2. por cada descendiente el de R: si el.shadowRoot no es null → recursión con R := el.shadowRoot, profundidad +1 si no, si el.nac3 es objeto con query() → delegar (raíz cerrada) 3. tope de profundidad: 10 niveles. Más abajo → not_found 4. recorrido en orden del DOM: hermanos antes que sombras anidadas. Gana el primero /* internos de referencia */ _deepQuery(selector, root) · _deepQueryAll(selector, root)

Raíces cerradas: son un límite del navegador, no una decisión de NAC3. El runtime no puede entrar salvo que el autor del componente exponga una superficie, voluntariamente.

interface NAC3HostInterface { query(selector): Element | null; /* OBLIGATORIO */ queryAll(selector): Element[]; /* recomendado */ describe?(): Array<{id, role, action?, label?}>; /* opcional */ } /* eventos de diagnóstico, deduplicados por anfitrión con un WeakSet, UNA vez por carga */ nac:shadow_blocked { host, reason: 'exposure_threw'|'not_exposed', ts } nac:shadow_protocol_violation { host, message, value_snapshot, ts }

  1. Poner data-nac-id, data-nac-role y data-nac-action en los elementos operables de adentro de la sombra.

Contrato de extensión de plugin — lienzo, iframes y APIs propias

en la batería

La ficha más grande del manual, y la que resuelve lo que NAC.click no puede: mandar un Send_UNO_Command a un iframe de Collabora, llamar figma.currentPage.selection = [...], invocar excalidrawAPI.setElements(...) sobre una referencia de React, o leer si «negrita» está activo en la selección actual, que la barra de herramientas refleja y el lienzo esconde.

La solución no fue extender NAC.click con heurísticas de detección. Fue agregar un verbo explícito y agnóstico que toma un slug y una ruta de verbo, y deja que el manifiesto del plugin declare cómo se enruta. El runtime no sabe nada de ninguna aplicación: aprende a hablarle leyendo el manifiesto.

NAC.registerPlugin(slug, manifest) → void /* manifiesto JSON puro, sin callbacks */ NAC.call(plugin, verb_path, args?) → Promise<any> NAC.read(plugin, state_path) → Promise<any> NAC.subscribe(plugin, event_path, cb) → SubscriptionHandle NAC.unsubscribe(handle) → void /* sincrónico e idempotente */

Verbos y eventos tienen exactamente una ligadura. El estado tiene un arreglo ordenado. read recorre la cadena en orden y devuelve la primera fuente que resolvió; si todas fallan, rechaza con state_unreadable y err.attempts trae una entrada por intento con {backend, reason}. La cadena codifica la preferencia del autor: la fuente más rápida, barata y fresca va primera.

Agregar un enrutador nuevo exige subir la versión de la especificación, y un runtime que no conoce un enrutador tiene que rechazar el manifiesto, nunca saltearlo en silencio. emitter-listen es la razón por la que este documento es 2.6 y no 2.5.3.

Seis formas, y no se componen: un extractor es exactamente una de estas filas. Un manifiesto que necesite transformar de verdad declara un script-bridge.

Dicen que el protocolo no pudo llegar, nunca por qué la aplicación dijo no. Un plugin que necesita un código propio —una fila que no está materializada, un documento bloqueado, una exportación todavía renderizando— lo levanta bajo el prefijo reservado plugin.:

const e = new Error('row 42 is not materialised');
e._code = 'plugin.row_not_materialized';
throw e;   /* adentro del enrutador al que el manifiesto dirige */

call y subscribe lo afloran textual en err.code. Un código que no es uno de los diez ni está bajo plugin. se rechaza como invalid, conservando la cadena rechazada en err.offending_code: un código no declarado que viajó igual es cómo un vocabulario deja de ser un vocabulario.

La regla de fallo cerrado de la 2.6, y el defecto que la produjo

synthetic-mutation resuelve cada ruta de estado observada al elemento que selecciona su ligadura primaria de dom-mirror. Cuando un selector no encuentra nada, subscribe tiene que rechazar con backend_target_missing, nombrando las rutas y los selectores que no resolvieron, y no devolver un asa.

Por qué: una suscripción que no observa nada resuelve bien y después nunca dispara — que es exactamente el daño silencioso que este protocolo existe para eliminar. Y hasta la 2.5.2 eso es lo que el runtime de referencia hacía.

Un manifiesto cuyo nodo observado legítimamente aparece y desaparece —la fila de una grilla virtualizada, que existe sólo mientras está en pantalla— declara root: un contenedor que sobrevive al nodo. El runtime observa el contenedor con subtree: true y vuelve a resolver los selectores en cada mutación, así que una suscripción tomada mientras el nodo estaba ausente dispara cuando el nodo se monta. Pasar de desconocido a conocido es el cambio que el llamador espera, así que esa transición también emite.

Los seis ganchos de la 2.6: descubrimiento y autodescripción

en la batería

Hasta la 2.5.2 el registro de extensión era legible por exactamente tres funciones (call, read, subscribe), así que un agente que no registró el plugin él mismo no podía enterarse de que existe. Leía el manifiesto del DOM, encontraba la cáscara, y la superficie del lienzo era invisible. Para una superficie que no declara DOM en absoluto —un plugin sólo de voz— no había nada que encontrar.

/* descubrimiento */ NAC.plugins() → PluginDescriptor[] /* ordenado por slug */ NAC.describePlugin(slug) → PluginDescriptor /* asas de API, para objetos que nunca llegan a window */ NAC.registerApiHandle(name, obj) · NAC.unregisterApiHandle(name) → boolean NAC.apiHandles() → string[] /* autodescripción, todo opcional */ verbo: label · hint · params[] params: {name, type, required?, unit?, min?, max?, enum?, label?, hint?} estado: label · hint · unit evento: label · hint
Las cinco reglas del descubrimiento, y por qué cada una
  1. Las dos son SINCRÓNICAS. Leen un objeto local; nada se despacha a ninguna superficie, así que no hay motivo para que un agente espere una vuelta sólo para saber qué hay.
  2. El descriptor es una COPIA. Un llamador no debe poder alcanzar el registro vivo a través de él y reescribir el enrutamiento de otro plugin.
  3. Vuelve ordenado por ruta, así que dos lecturas del mismo registro son comparables byte a byte.
  4. Un label, hint o params no declarado se lee como null, nunca como clave ausente: el lector no tiene que distinguir «ausente» de «no declarado».
  5. describePlugin sobre un slug no registrado rechaza con plugin_not_registered.

El descubrimiento es deliberadamente una lectura de lo que el manifiesto declara, no un sondeo de la superficie. Dice qué existe y cómo nombrarlo; si la superficie contesta hoy es lo que call y read están para averiguar.

Y lo que cierra la autodescripción: en una superficie continua lo accionable es el argumento —una coordenada y un zoom, un instante de una línea de tiempo, una página y un campo de formulario, una pose en tres dimensiones— y hasta la 2.5 nada declaraba su forma, su unidad ni su rango. Un corredor de voz no podía ni nombrar el verbo en voz alta.

Y un límite explícito

params declara la forma del objeto args que recibe NAC.call. El runtime NO valida los argumentos contra él. La declaración existe para que un agente pueda componer una llamada y un corredor de voz pueda pronunciarla; una superficie que necesita sus argumentos exigidos los exige donde aterrizan.

Y nada de esto lo traduce el runtime: una etiqueta se escribe en el idioma de la aplicación, y un anfitrión que habla otro localiza en su propia capa.

Arranque, reproducción diferida y el arnés de pruebas

Cuando el módulo se instala hace cinco cosas, en este orden, y conviene conocerlas porque explican casi todos los problemas de arranque:

  1. Instala global.NAC con sus claves exportadas.
  2. Se protege de una doble instalación con la bandera __nac_v1_installed.
  3. Despacha nac:installed llevando { version, spec }.
  4. Monta el puente de ARIA, para que data-nac-a11y-hint llegue de verdad a un lector de pantalla. Corre después de instalar, y agrega a los aria-describedby existentes en vez de pisarlos.
  5. Reproduce window.__NAC_PENDING__, el buffer que el anfitrión apiló antes de que el runtime existiera, y después lo limpia para que una recarga en caliente no lo reproduzca dos veces.
/* el buffer de arranque: el anfitrión apila {event, detail} ANTES de que el runtime cargue */ window.__NAC_PENDING__ = [{ event: 'nac:action:succeeded', detail: {...} }, ...]; NAC.replay_pending(buffer) /* reproducir a mano, si el automático no alcanza */ /* arnés: el runtime se puede probar a sí mismo */ NAC.assert_event_fired(tipo, opts?) · NAC.assert_event_count(tipo, n) NAC.perf_probe(...) · NAC.set_perf_tolerance(...)

Los tres niveles de conformidad

su candado necesita navegador, fuera de CI

Un nivel se escribe NAC3 Conformance Level 1, 2 o 3. Una afirmación de conformidad tiene que citar el identificador publicado en api/latest/levels.json —nac3-conformance-level-<1|2|3>— y nunca un nombre para mostrar.

Por qué se renombraron en la 2.5

Antes se escribían NAC-1, NAC-2 y NAC-3. Eso está a un guion del nombre del protocolo: «esta página es NAC-3 conforme» no se podía distinguir de «esta página implementa NAC3», y un agente al que le pedían reportar un nivel no tenía una cadena sin ambigüedad para reportar. Los nombres viejos siguen legibles como alias históricos (legacy_display_name al lado de su nivel) pero no son normativos.

NivelLo que exige, además de todo lo del nivel anterior
1Todo widget clicable que un agente deba poder operar lleva data-nac-id y data-nac-role · todo action dispara nac:action:succeeded después de su efecto · la página registra al menos un manifiesto · NAC.click(id) funciona para cada id anunciado.
2Declara tabs[], fields[] y actions[] explícitos en el manifiesto, no inferidos del DOM · label_i18n con los diez idiomas para toda etiqueta de cara al usuario · implementa los primitivos de migración de la 2.0 · pasa validate_global({probe:false}) con cero hallazgos de severidad error.
3Manifiestos firmados con HMAC · distingue isTrusted para verbos sensibles · pasa validate_global({probe:true}) con cero hallazgos, de cualquier severidad.
