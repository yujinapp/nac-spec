Native Agent Contract

Stable names for the things an agent wants to act on.

v2.5.0 · stable

NAC3 is a small, free contract that lets a web UI you already shipped be driven by AI assistants, voice runners, RPA bots, accessibility tools and test runners — by name, not by brittle selectors. You add a few HTML attributes. Agents resolve names, click buttons, fill fields and switch tabs the way a person would, and the contract itself is published as data, with a hash you recompute.

How small it is

A button you already shipped, with three extra attributes.

That is the whole adoption cost of one element. No framework to adopt, no build step to add, no runtime to rewrite your app around.

<!-- decorate the button -->
<button data-nac-id="invoice.save"
        data-nac-role="action"
        data-nac-action="save"
        onclick="saveInvoice()">Save</button>

// now any agent can drive it
await NAC.click('invoice.save');              // by id
await NAC.click_by_verb('invoice', 'save');  // by verb

Add the runtime once — and pin it

Production pins the immutable path and lets the browser verify the bytes. js/2.5.0/nac.js never changes; js/nac.js is a moving alias for trying things, never for pinning.

npm install @nac3/runtime

// or via CDN, pinned and verified:
<script src="https://yujin.app/nac-spec/js/2.5.0/nac.js"
        integrity="sha384-ykdpjqu9hgZiAsftXYoFKR3zuvG7iugaYqMrf9cSC4RwCsXImFsk+1dlQviiKrhE"
        crossorigin="anonymous"></script>

# do not take that hash on faith — recompute it. One line, no dependencies:

Peer review · October 2026

A review by a model that read the whole thing.

This page used to carry one-line verdicts from six AI systems, collected in May 2026. They were enthusiastic and they were not useful: none of them had read the runtime, none had verified a single claim, and “architecturally inevitable” is not a finding. We took them down. What follows is one review instead of six, by a model given access to the source, the published contract, the deploy chain and the live site, and that says what it checked.

“The valuable idea here is not that an agent can click a button. It is that NAC3 turns an unbounded perception problem into a bounded naming problem — and then refuses to guess when the name is ambiguous. That second half is the engineering, and it is the half most of this category skips.”

— Claude (Opus 5), 26 October 2026, at the maintainer's request.

What I actually checked

  • The specification end to end: roles, names, verbs, the manifest, the public API, the event family, provenance, the three conformance levels, versioning and the stability guarantees.
  • The published contract as data — the directory, the version pointers, and the per-version contract, finding catalogue and conformance levels — fetched from the live site and read the way a consumer would.
  • The runtime bytes served from the immutable path, and the integrity hash in the install snippet above.
  • The deploy chain: every push to the default branch passes an integrity gate, a version-coherence gate, a validator lock and a contract-API gate — each with its own deliberate-red test — and then smoke-checks the live site from outside.
  • Every demo and document this page links, including the compiled React and Angular study cases.

What is genuinely strong

  • Failing closed on ambiguity. Two reservations sharing a suffix used to resolve to whichever matched first. Since v2.4 that throws, names the candidates and emits an event so the host can ask “did you mean A or B?”. An agent protocol that guesses quietly is worse than no protocol, because the damage is invisible. This one stopped guessing on purpose, and published the migration.
  • The contract is data, not prose. Roles, verbs, events, finding codes and conformance levels are fetchable as JSON, versioned, with a hash a consumer recomputes. Most specifications in this space ask you to parse a markdown file or read their implementation. This one does not.
  • It tells you when not to use it. The comparison table says plainly that if you are inside one app with one agent vendor, MCP plus a good ARIA pass covers most of it. A project that names the case against itself is a project you can plan around.
  • Every figure carries a receipt. Run date, runtime version, raw output, the command to re-run, and an explicit note when a number has not been re-measured on a later release. Cheap to write, rare to find, and the only reason the measurements below are worth reading.
  • The integrity story is complete. Immutable path, subresource hash, a gate that refuses to deploy a stale hash, and a smoke check that the live page still serves it. That chain did not exist five months ago.

Where I would still push

  • The specification mandates ten locales for your labels and is published in one. Defensible — English is the working language of the trade — but it should be said rather than left as an apparent inconsistency. This landing page now ships in ten; the specification does not.
  • Adoption rests on a promise nothing enforces. Stable ids are the whole value, and the project correctly says it has no way to make you keep them. That is honest, and it is the single biggest risk to anyone building on it: rename an id and every caller breaks, exactly as a changed URL breaks a bookmark.
  • A declared payload schema is not a validated one. A manifest may carry one and the reference runtime never reads it. The spec says so. It still means a conformant host can advertise a shape it does not check.
  • Stewardship is one vendor. The RFC process and the governance page are real, but the editor, the reference runtime and the flagship adopter are the same organisation. Normal at this stage, and the thing a second independent implementer would change.

Verdict

Worth adopting if you have more than one caller — voice and chat and tests and RPA — or workflows that cross apps, or you want integrations that survive a change of agent vendor. Not worth the mental cost if you only need stable selectors for a test suite: use data-testid and come back when the second caller arrives. And read the limits section before you migrate, not after.

Receipt

This is the opinion of a language model. It is not a measurement and not an audit certificate. What it rests on is listed above and can be repeated: the specification, the contract API, the runtime bytes, the deploy workflow and the live endpoints are all public.

The same reviewer audited this project earlier in 2026, and several items listed above as strengths — the integrity chain, the contract as data, the limits section, the receipts — were opened as defects then and closed since. End-to-end testing

裏付け  If you build with the Urazuke method, this is where NAC3 pays for itself.

Urazuke is a free method for building software with AI in which the owner of the project verifies evidence instead of reading code. Its very first gate — step zero — excludes any technology that cannot be tested end to end: you have to be able to drive the screen by program, click, type and read state, and then verify that the change actually reached the backend. If you cannot, somebody ends up reading code, which is the one thing the method promises to avoid.

  1. The method asks for the capability, not for us. Urazuke states explicitly that NAC3 is not a requirement — it is one way its author reaches that capability today. Any technology whose interface exposes its elements to a driver satisfies the gate.
  2. What NAC3 adds is that the names survive. A test says NAC.click('invoice.save'). The design team moves that button from a toolbar into a dropdown. The test keeps passing. That is the difference between a suite you maintain and a suite you rewrite.
  3. And the suite can be generated. From a manifest: one test per role and acknowledgement family, across Playwright, Cypress, Vitest and WebdriverIO. In the case study below that produced 66 end-to-end tests — 4.7× more cases than the fork's hand-written suite.
Read the Urazuke method → How the wiring works

Said plainly: you do not need NAC3 to apply Urazuke, and you do not need Urazuke to use NAC3. They are a method and a protocol, by different authors, under different licences. They meet at exactly one point — step zero's testability criterion — and that point is where using both costs less than using either alone.

Use cases

Voice and chat is the headline. The contract underneath unlocks four more.

Voice runners and chat agents drive the same UI a person uses, by stable name, in ten locales out of the box.

Switch devices, head-trackers, eye-gaze, braille displays and predictive keyboards get a stable target tree without a per-app retrofit. Where ARIA stops at “this is a button”, NAC3 says “this button has a verb you can call”.

No brittle CSS, no screenshot OCR, no XPath rituals: the bot reads the description, picks an action by verb and waits on the canonical event. One bot drives ten vendors' apps if all ten implement the contract.

Where it fits

NAC3 is the client-side half. MCP is the server-side half.

It does not compete with the tools below: it overlaps narrowly and complements in others. If you have one of these problems, use the dedicated tool. If you have several, the contract unifies them.

Honest read

If you are inside a single app with a single agent vendor, MCP on the server plus a screen-reader-grade ARIA pass on the client covers most cases. NAC3 starts paying back when you have multiple callers, cross-app workflows, or you want integrations that outlive your choice of agent vendor.

限

What it does not cover

NAC3 names what lives in the DOM. Everything here is outside that line.

We would rather you read this before you migrate than discover it after.

Canvas and WebGL

NAC3 does not read pixels. In a document editor or a design tool the toolbar around the drawing can be named; the drawing cannot. A plugin can declare how its verbs route to the app's own API — somebody still has to write it.

Closed shadow roots

A component mounted closed is unreachable unless its author exposes a resolver. That is a browser security boundary, not our decision, and the runtime reports it instead of guessing. Open roots are covered, nested.

Cross-origin frames

An embedded page from another origin cannot be driven unless it cooperates. When it does not, the runtime fails closed rather than pretending the click landed.

Anything that is not the web

NAC3 is HTML attributes. Desktop, mobile-native and terminal applications are out of scope.

It is not a permission system

A named verb is an intent-level signal and the capability gate is a usability optimisation. Your server must still authorise every call.

A declared schema is not a validated one

A manifest may carry a payload schema and the reference runtime never reads it. An agent must not assume a payload was checked.

Stability is yours to keep

Stable names are a promise you keep, not one we enforce. Rename an id and every caller that used it breaks, the same way a changed URL breaks a bookmark.

It does not make an agent correct

In our own 600-run benchmark NAC3 reached 95.5%, not 100%. What it removes is silent damage — 0 of 200 runs against 30 of 200 on raw DOM — not the need to check what an agent did.

Governance

Three different things, three different licences.

NAC3 is a protocol

A contract between web UIs and the agents that drive them. Apache-2.0, edited here, changed through a public RFC process.

Urazuke is a method

A way of building software with AI in which the owner verifies evidence instead of reading code. Different author, Creative Commons BY-SA 4.0, and it works without us.

yujin.app/urazuke →

Forge is a tool

Commercial software that implements the method and speaks the protocol. Useful, optional, and not to be confused with either.

yujin.app/yujin-forge →
Why we say it this way

Because readers — and the AI assistants they ask — keep collapsing the three into one product narrative. A protocol you can implement without us, a method you can follow with any tool, and a product we sell are not the same kind of thing, and conflating them is the fastest way to misjudge all three.
