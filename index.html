How small is small

A button you already shipped, with three extra attributes:

<!-- Decorate the button -->
<button data-nac-id="invoice.save"
        data-nac-role="action"
        data-nac-action="save"
        onclick="saveInvoice()">
  Save
</button>

// Now any agent can drive it:
await NAC.click('invoice.save');              // by id
await NAC.click_by_verb('invoice', 'save');   // by verb

Add the runtime once. Production pins the immutable path and verifies it with a hash:

npm install @nac3/runtime
// or via CDN:
<script src="https://yujin.app/nac-spec/js/2.5.0/nac.js"
        integrity="sha384-ykdpjqu9hgZiAsftXYoFKR3zuvG7iugaYqMrf9cSC4RwCsXImFsk+1dlQviiKrhE"
        crossorigin="anonymous"></script>

Which URL. js/2.5.0/nac.js is immutable -- those bytes never change, so pin it in production. js/nac.js is a moving alias that always serves the newest build; use it only to try things, never to pin. The integrity attribute makes the browser refuse a file that does not match the published hash, so a corrupted or substituted download fails loudly instead of running.

Recompute the hash yourself. Do not take the value above on faith:

# one line, no dependencies -- prints the same string that is in the tag
node -e "const c=require('crypto'),f=require('fs');console.log('sha384-'+c.createHash('sha384').update(f.readFileSync('nac.js')).digest('base64'))"
# in this repository the same check runs as a gate
node scripts/build-integrity.mjs

Use cases

Voice + chat is the headline. The contract underneath unlocks four more.

Voice + chat

Voice runners (Siri-style, Whisper-fed, browser SpeechRecognition) and LLM chat agents drive the same UI a human uses, by stable name. Multi-locale out of the box (10 languages). The headline use case.

Accessibility

Users with motor impairment can drive the app by switch device, head-tracker, or eye-gaze through a NAC-aware adaptor -- without per-app retrofit. Braille displays, sip-and-puff controllers, and Dasher-style predictive keyboards get a stable target tree to render. Where ARIA stops at "this is a button," NAC says "this button has a verb the assistive tool can call."

Testing & QA

Stable names that survive UI redesigns. Test code says NAC.click('invoice.save'), the design team moves the button from a toolbar to a dropdown, the test keeps passing. Selenium, Playwright, Cypress, and headless browsers all consume the same contract. Auto-generated test corpora (per role + ack family) make near-100% coverage cheap.

RPA

Robotic process automation traditionally scrapes the DOM with brittle CSS selectors that break on every UI change. With NAC, an RPA bot reads NAC.describe(), picks an action by verb, calls it, and waits on the canonical event family. No screenshot OCR, no XPath rituals. The same bot drives ten different vendors' apps if all ten implement NAC3.

Agentic control

LLM agents (Claude, GPT, Gemini, local models) drive web UIs by name without per-app fine-tuning. Cross-app interop (v2.3 preview): a host agent imports a peer app's tree via MCP and proxies dispatches. "Yujin, jump to Excel" becomes one extra MCP call. The contract scales to a marketplace of NAC3 apps each addressable from any agent.

Why NAC, why now

Voice assistants, LLM chat agents, and accessibility tools all face the same problem: they need stable names for the things they want to act on. CSS selectors break when you redesign the UI. ARIA was designed for human-driven assistive tech, not agent-driven automation, and its contract stops at "this is a button" rather than "this button has a verb the agent can call".

Today every team builds its own per-app glue: a custom voice grammar, a hand-written automation script, a one-off accessibility shim. That work does not transfer between apps, between teams, or between agent vendors.

NAC is a small experimental contract that lets those agents talk to those apps without per-pair integration. ARIA stays in place for the accessibility tree; NAC adds a parallel agent tree on the same elements.

Where NAC3 fits in the agent stack

NAC3 is the client-side half of agent-driven software. MCP is the server-side half. Use both for full-stack agents: MCP exposes your business logic, NAC3 exposes your UI.

NAC3 does not compete with any of these tools -- it overlaps in narrow ways and complements in others. If you only have one of the problems below, use the dedicated tool. If you have several, NAC3 unifies the contract.

LayerWhat it solvesWhere it stopsNAC3 relationship
MCP (Anthropic) Agent calls server-side tools / functions Does not touch the UI; agent cannot navigate, fill forms, or read on-screen state Complement. Use MCP for backend ops, NAC3 for the UI half. v2.3 preview adds an MCP bridge to route between NAC3 apps.
ARIA Accessibility tree for screen readers + switch devices Stops at "this is a button named Save"; no verb the agent can call, no completion event Sits next to. Keep your ARIA roles. Many adopters end up with role="button" and data-nac-role="action" on the same element.
data-testid Stable selectors for test runners (Cypress, Playwright) Test-only; no manifest, no event family, no provenance, no i18n Superset. NAC3 covers the testing case + voice + RPA + LLM with the same attribute, but at a higher mental cost. If you only need tests, data-testid is fine.
AG-UI (CopilotKit) Agent-to-app protocol for chat-driven UIs Tied to the CopilotKit framework + JS runtime; less focus on RPA / a11y / cross-vendor LLMs Adjacent. Different bet on the same space. AG-UI has Series A funding and an existing ecosystem; NAC3 is open and framework-agnostic but earlier-stage. Pick AG-UI if you build on CopilotKit; NAC3 if you want a framework-neutral surface.
Computer Use / browser-use (vision-based) Agent reads pixels, reasons over screenshots Slow, expensive, brittle on dynamic content; depends entirely on the LLM Fallback layer. Vision is what the agent uses when NAC3 is not there. NAC3 turns a 3-second pixel-reasoning round into a 30 ms named dispatch.

Honest read: if you are inside a single app with a single agent vendor, MCP (server) + a screen-reader-grade ARIA pass (client) covers most cases. NAC3 starts paying back when you have multiple callers (voice + chat + RPA + tests), cross-app workflows, or you want vendor-portable integrations.

What NAC3 does not cover

NAC3 names what lives in the DOM. Everything below is outside that line. We would rather you read it here than discover it after you migrate.

Canvas & WebGL

Canvas and WebGL surfaces. NAC3 does not read pixels: in a document editor, a design tool or a custom WebGL canvas, the toolbar around the drawing can be named, the drawing itself cannot. v2.5 adds a contract so a plugin can declare how its verbs route to the app's own public API (postMessage, plugin SDK), and the runtime learns one app only by reading that plugin's manifest -- somebody still has to write it.

Closed shadow roots

Closed shadow roots. A web component mounted with attachShadow({mode:'closed'}) is unreachable unless its author voluntarily exposes a resolver -- that is a browser security boundary, not a NAC3 decision -- and the runtime reports it (nac:shadow_blocked) instead of guessing. Open shadow roots are covered, nested.

Cross-origin frames

Cross-origin frames. An embedded page from another origin cannot be driven unless it cooperates -- it has to run NAC3 and accept the message -- and when it does not, the runtime fails closed with cross_origin_blocked rather than pretending the click landed.

Anything not web

Native and non-web applications. NAC3 is HTML attributes: desktop, mobile-native and terminal applications are out of scope.

Not a permission system

NAC3 is not a permission system. A named verb is an intent-level signal and the capability gate is a UX optimisation; your server must still authorise every call.

Declared is not validated

A declared payload schema is not a validated one. A manifest may carry payload_schema and the reference runtime never reads it, so an agent MUST NOT assume a payload was checked.

Stability is yours to keep

Stable names are a promise you keep, not one we enforce. NAC3 asks ids to survive redesigns and has no way to make them: rename an id and every caller that used it breaks, the same way a changed URL breaks a bookmark.

It does not make an agent correct

It does not make an agent correct. In our own 600-run benchmark NAC3 reached 95.5%, not 100%. What it removes is silent damage -- 0 of 200 runs, against 30 of 200 on raw DOM -- not the need to check what an agent did.

Three different things, three different licenses. NAC3 is a protocol -- this site, Apache-2.0. Urazuke is a method for building software with evidence -- yujin.app/urazuke, Creative Commons BY-SA 4.0. Yujin Forge is a commercial tool that implements both. You can adopt the protocol without the method and without the tool; that is the point of publishing it under Apache-2.0.

One more limit lives in its own section, because it is about who steers the contract rather than what it reaches: NAC3 is stewarded by one company, not a foundation. Read it in Governance, below.

The specification in other languages

The normative text of NAC3 is the English one: SPEC.html. It is also published as nine machine translations, and those are non-normative. None of them is complete, and where a translation and the English text disagree, the English text governs -- a conformance claim is a claim against the English text. Each page states at the top, in its own language, which revision of the English text it translates and how much of the current text it carries.

Español · Português · Français · Italiano · Deutsch · 日本語 · 中文 · हिन्दी · العربية

We publish them anyway because a partial translation a reader can check against the English text is worth more than no translation -- as long as the page says which one governs before the reader starts trusting it. Bringing them up to the current text is open work, not a silent gap. The ten-locale requirement of section 4.3 is a requirement on the labels in your manifest, not on the language of this document.

Governance

NAC3 is stewarded by Yujin today -- one company, not a foundation. We say this up front because the difference matters: NAC3 is not yet an industry standard the way ARIA or MCP are. It is a vendor-authored contract published under permissive licenses (Apache 2.0 spec + Apache 2.0 runtime) so adopters do not depend on Yujin's continuity.

Spec changes follow an RFC process with at least 14 days of public comment for any change to the public API or wire format. We commit to moving NAC3 to a neutral foundation (W3C community group, Linux Foundation, or equivalent) if and when adoption justifies neutral governance. Until then, the Apache 2.0 licensing (spec + runtime) is what guarantees portability -- adopters can fork it, run it, and ship it, today and after we are gone.
